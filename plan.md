# Pace Arena — implementation plan

## Product and architecture

Pace Arena is a demo-only peer-to-peer football gaming challenge platform, initially for players in Kenya. Keep the initialized React 19/Vite, Express/tRPC, Drizzle and managed-MySQL stack; the existing project already enables the persistent server and database, so do not add a parallel database vendor. The client uses typed tRPC calls and Wouter routes. The Express backend owns authentication, authorization, all state transitions, database transactions, password-reset email, evidence storage and timeout processing. Use additive, checked-in migrations and never send an authoritative balance, role, deadline or match status from the browser.

Implement email/password accounts with no email-verification requirement. Validate the browser origin and rate-limit signup/login; create the user, profile, wallet, one-time starter grant and session so registration immediately opens the app. Preserve access for legacy accounts whose `emailVerifiedAt` is unset, but do not claim that their address was verified. Keep expiring single-use password-reset links, hashed opaque sessions and protected Player/Admin procedures. The Pace Arena cookie is `pace_arena_session`; set `SameSite=None; Secure` when the trusted public forwarded protocol is HTTPS for Preview, and use a separate development-safe policy for plain HTTP. SMTP credentials are server-only and needed for password reset, not signup. Email allowlists never grant admin. Only an existing administrator may grant or revoke another account's role through an authenticated, reason-required, audited server transaction; preserve existing roles and prevent removal of the final administrator.

Persist normalized profiles, exact game/device compatibility preferences, challenges, matches, participants, private codes, evidence metadata, wallet accounts, ledger entries, disputes, notifications, state history and administrator audit events. Lock wallet/challenge/match rows for atomic reserve, accept, refund and settlement; validate idempotency, eligibility, stake bounds, participant ownership and allowed transitions on the server. Support public challenges and optional private username invitations: validate that the invited profile is currently eligible, available and exactly compatible; list an open invite only to its creator and intended recipient; let the recipient accept once or decline to refund the creator.

The managed MySQL service does not provide native application Row-Level Security. All database access stays server-side behind authenticated tRPC procedures with per-user relationship predicates and admin-role middleware; no database credentials reach the browser. The platform object store has no per-object ACL. Encrypt evidence with AES-256-GCM, keep random object keys server-side, record match ownership in MySQL, and stream images only through authenticated participant/admin endpoints with `private, no-store` headers. Validate image signatures and the 5 MB cap before storage. Screenshots are player-submitted evidence, not independently authenticated proof.

Model match states explicitly (DRAFT, OPEN, ACCEPTED, AWAITING_STAKES, READY, IN_PROGRESS, AWAITING_EVIDENCE, UNDER_REVIEW, COMPLETED, DRAWN, CANCELLED and REFUNDED). Use backend-generated readiness, play and five-minute evidence deadlines; persist notifications and state/audit history. Idempotent row-locked timeout processing refunds abandoned reservations or escalates missing/conflicting score reports to review—it never silently awards credits. Provide reason-required admin dispute decisions and demo-ledger adjustments, plus audited controls to pause new challenge creation, adjust stakes only within the 10–5,000-credit demo ceiling, set the default match duration from 6–30 minutes, and post a short player-facing operational notice. Those settings apply only to new challenges; no payments, purchases, deposits, withdrawals, cash prizes or cash-out.

## Project structure

- `client/src/App.tsx`: route declarations and authenticated/admin route guards; `client/src/pages/`: landing, email/password auth, dashboard, player directory, challenges/invitations, match/evidence, wallet/ledger, notifications, profile, disputes and administration.
- `client/src/components/`: responsive app shell/navigation, accessible states and reusable controls; `client/src/index.css`: design tokens, layouts, motion and responsive states; `client/public/manus-routes.json`: complete static page-route manifest; `client/public/brand-icon.svg`: site favicon.
- `server/_core/`: Express, sessions, auth and environment wiring; `server/auth.ts`: registration/login/reset/session procedures; `server/arena.ts`: profile, compatibility, invitations, challenges, wallet, match lifecycle, evidence metadata, disputes, notifications and audited admin procedures including role changes; `server/evidence.ts`: authenticated encrypted-file delivery; `server/db.ts`: application persistence.
- `drizzle/schema.ts` and `drizzle/`: relational schema plus additive versioned migrations; `shared/pace.ts`: game/platform compatibility, lifecycle contracts and bounds.
- Root `README.md`, `plan.md`, `TODO.md`, `.env.example` and `app.config.ts`: project operation guide, source acceptance criteria, placeholder settings and platform logo metadata.

## Design direction

- Quiet graphite sports editorial: probability 0.04.
- Retro arcade tournament poster: probability 0.02.
- Broadcast control-room dashboard: probability 0.08.

Choose **quiet graphite sports editorial**, inspired by independent football-culture print and modern esports scoreboards. **Core principles:** terms before hype; eligibility and result status always legible; every high-stakes action has a clear consequence; compact layouts stay calm on mobile. **Color philosophy:** graphite and ink create focus, warm white carries score/terms, slate tones de-emphasize secondary data, and ownable electric lime (`#B7F34A`) is reserved for active/primary states. **Layout paradigm:** a fixed desktop competition rail beside an editorial workspace, translated to compact cards and a bottom mobile bar rather than a centered marketing grid. **Signature elements:** split-pitch P/A mark, restrained halfway-line geometry and a lime score pip. **Interaction philosophy:** honest inline guidance; explicit confirmation before accepting/cancelling/settling; keyboard-visible focus and accessible status labels. **Animation:** quick 120–180 ms fades/slides, no decorative pulsing beyond a restrained active dot, and reduced-motion support. **Typography:** Space Grotesk display headlines with a highly readable system/Inter-style sans for body and forms; large numerals for credits and scores. **Brand essence:** a clear-terms, demo-credit football challenge arena for players who want a fair path from fixture to final whistle; competitive, candid and grounded. **Brand voice:** short, confident and transparent. Examples: “Find your next fixture.” “Demo credits only. The result is still yours to earn.” **Wordmark/logo:** custom split-pitch P/A monogram with a compact Pace Arena wordmark; never use publisher logos. **Signature brand color:** `#B7F34A` electric lime.

## Delivery boundaries

Build and test against the project's existing resource configuration. Development, published production and migrations share the managed database: apply only checked-in, additive schema changes and avoid destructive data tests. Configure SMTP using protected project secrets only for password-reset email; do not keep an email-based admin allowlist. Runtime timeout polling is process-local but every database transition is revalidated under row locks; do not claim realtime push. Provide operational limitations and backup guidance in the README. Do not claim gaming-publisher affiliation, independent screenshot authentication, licensing or legal compliance. Any future Kenyan real-money feature requires separate legal classification/licensing review and payment-provider approval.
