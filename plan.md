# Pace Arena — implementation plan

## Product and architecture

Pace Arena is a peer-to-peer football gaming challenge platform for players in Kenya. Keep the initialized React 19/Vite, Express/tRPC, Drizzle and managed-MySQL stack; the existing project already enables the persistent server and database, so do not add a parallel production database vendor. The client uses typed tRPC calls and Wouter routes. The Express backend owns authentication, authorization, KES wallet state, signed partner-credit events, all wallet/challenge/match transitions, password-reset email, private evidence storage and timeout processing. Use additive, checked-in migrations and never accept an authoritative balance, role, deadline, partner settlement or match status from the browser.

Implement email/password accounts with no email-verification requirement. Validate the browser origin and rate-limit signup/login; create the user, profile and session so registration immediately opens the app. Do not create demo wallets or grant demo starter credits to new accounts. Preserve access for legacy accounts whose `emailVerifiedAt` is unset, but do not claim that their address was verified. Keep expiring single-use password-reset links, hashed opaque sessions and protected Player/Admin procedures. The Pace Arena cookie is `pace_arena_session`; set `SameSite=None; Secure` when the trusted public forwarded protocol is HTTPS for Preview, and use a separate development-safe policy for plain HTTP. SMTP credentials are server-only and needed for password reset, not signup. Email allowlists never grant admin. Only an existing administrator may grant or revoke another account's role through an authenticated, reason-required, audited server transaction; preserve existing roles and prevent removal of the final administrator.

Retire demo-credit wallets, demo starter grants and new demo-staked matches from player-facing flows. Do not delete existing users, demo wallet balances or historical ledgers; preserve them as non-cash read-only records for authorized audit/history. Existing in-progress demo matches may complete only under their original terms in the historic demo ledger. Never convert demo credits into KES. New challenges use KES only and are unavailable until the server-side real-wagering gate is deliberately enabled.

The owner's separate partner website handles checkout/STK and decides when its payment is settled. Pace Arena displays a configured HTTPS external purchase link and a random, stable KES wallet reference for the player. The partner server then sends a `credit` or `reversal` event to `POST /api/partner/v1/credit-events`. Authenticate the exact raw JSON bytes using HMAC-SHA256 in `X-Pace-Signature: sha256=<hex>` with `X-Pace-Timestamp` as Unix seconds and a server-only shared secret. Accept timestamps only within five minutes, use constant-time comparison, validate KES integer amount/currency and wallet reference, and uniquely deduplicate partner event/transaction IDs. A browser redirect, unsigned request, replay, malformed event or client-claimed payment can never alter a wallet. Persist the signed partner event and KES ledger entry atomically; unknown/refunded/duplicate outcomes must not create extra spendable balance. Do not call MegaPay, send STK prompts, collect provider credentials, or infer partner settlement from frontend state in Pace Arena. Wallet activation fails closed unless the external HTTPS purchase URL, callback secret and positive limits are configured. The partner integration contract and example payload/signing rules live in `PARTNER_INTEGRATION.md`.

Keep the KES wallet separate from legacy demo data. The server creates KES accounts with stable random wallet references, records integer whole-shilling amounts, and maintains available/reserved balances plus an append-only idempotent transaction ledger. A player may request a manual withdrawal to a normalized Kenyan M-Pesa number; reserve funds atomically and expose a request to the administrator. An authorized administrator sends the payout outside Pace Arena through the approved business account and records the external receipt/reference and reason, or rejects with a reason and atomically releases the reserve. The application never initiates a payout transfer.

Gate KES wallet credits/withdrawals behind `PACE_KES_WALLET_ENABLED` and new KES match creation/acceptance/settlement behind `PACE_REAL_WAGERING_ENABLED`; both default off and are server-only. Require a sufficiently long partner HMAC secret, configured external purchase URL and server-side integer KES limits before enabling any wallet action. Require administrator-verified cash-wallet eligibility before funds are made spendable or withdrawn. Never silently fall back to demo credits when a real-money path is unavailable. Do not run live partner callbacks, payments, payouts or fake monetary writes during tests. The managed MySQL database is shared by Preview and publication; test partner callbacks with mocks and apply only additive migrations.

Model match states explicitly (DRAFT, OPEN, ACCEPTED, AWAITING_STAKES, READY, IN_PROGRESS, AWAITING_EVIDENCE, UNDER_REVIEW, COMPLETED, DRAWN, CANCELLED and REFUNDED). Use backend-generated readiness, play and five-minute evidence deadlines; persist notifications and state/audit history. Idempotent row-locked timeout processing refunds KES reservations or escalates missing/conflicting score reports to review—it never silently awards money. New KES settlements and all refunds remain in KES. Provide reason-required admin dispute decisions and KES-ledger review, plus audited controls to pause new challenge creation, set server-configured KES limits, set the default match duration from 6–30 minutes, and post a short player-facing operational notice. Historic demo settings never control KES terms.

The managed MySQL service does not provide native application Row-Level Security. All database access stays server-side behind authenticated tRPC procedures with per-user relationship predicates and admin-role middleware; no database credentials reach the browser. The platform object store has no per-object ACL. Encrypt evidence with AES-256-GCM, keep random object keys server-side, record match ownership in MySQL, and stream media only through authenticated participant/admin endpoints with `private, no-store` headers. Validate file signatures and size limits before storage. Screenshots and recorded video are player evidence, not cryptographic proof or independently authenticated game results.

## Project structure

- `client/src/App.tsx`: route declarations and authenticated/admin route guards; `client/src/pages/`: landing, auth, dashboard, player directory, challenges/invitations, match/evidence/recording, KES wallet, notifications, profile, disputes and administration.
- `client/src/components/`: responsive app shell/navigation, accessible states and reusable controls; `client/src/index.css`: design tokens, layouts, motion and responsive states; `client/public/manus-routes.json`: complete static page-route manifest; `client/public/brand-icon.svg`: site favicon.
- `server/_core/`: Express, sessions, auth and environment wiring; `server/auth.ts`: registration/login/reset/session procedures; `server/arena.ts`: profile, compatibility, invitations, KES-only new challenges, legacy match handling, disputes, notifications and audited admin procedures; `server/kes-wallet.ts`: KES ledger, signed partner credits/reversals and manual withdrawals; `server/_core/index.ts`: raw-body partner callback and private recording route registration; `server/match-recordings.ts`: authenticated encrypted clip delivery and retention cleanup; `server/db.ts`: persistence.
- `drizzle/schema.ts` and `drizzle/`: relational schema plus additive versioned migrations; `shared/pace.ts`: game/platform compatibility, lifecycle, currency and money-validation contracts.
- Root `README.md`, `plan.md`, `TODO.md`, `.env.example` and `app.config.ts`: project operation guide, source acceptance criteria, placeholder settings and platform logo metadata.

## Design direction

Reuse the existing **quiet graphite sports editorial** direction, inspired by independent football-culture print and modern esports scoreboards. **Core principles:** terms before hype; eligibility and result status always legible; every high-stakes action has a clear consequence; compact layouts stay calm on mobile. **Color philosophy:** graphite and ink create focus, warm white carries score/terms, slate tones de-emphasize secondary data, and ownable electric lime (`#B7F34A`) is reserved for active/primary states. **Layout paradigm:** a fixed desktop competition rail beside an editorial workspace, translated to compact cards and a bottom mobile bar rather than a centered marketing grid. **Signature elements:** split-pitch P/A mark, restrained halfway-line geometry and a lime score pip. **Interaction philosophy:** honest inline guidance; explicit confirmation before accepting/cancelling/settling or requesting a withdrawal; keyboard-visible focus and accessible status labels. **Animation:** quick 120–180 ms fades/slides, no decorative pulsing beyond a restrained active dot, and reduced-motion support. **Typography:** Space Grotesk display headlines with a highly readable system/Inter-style sans for body and forms; large numerals for balances and scores. **Brand essence:** a clear-terms football challenge arena for players who want a fair path from fixture to final whistle; competitive, candid and grounded. **Brand voice:** short, confident and transparent. Examples: “Find your next fixture.” “KES wallet actions are recorded. Manual withdrawals are not sent by this app.” **Wordmark/logo:** custom split-pitch P/A monogram with a compact Pace Arena wordmark; never use publisher logos. **Signature brand color:** `#B7F34A` electric lime.

## Match recording

Offer explicit, user-initiated browser screen capture on supported desktop browsers; the user chooses a screen/window and can stop sharing at any time. Start recording only after the server reports the match `IN_PROGRESS`, stop on match end, and also allow each participant to upload a locally recorded clip for console/mobile gameplay. Videos are supplementary evidence: compare the two participants' submitted score reports, but do not claim reliable automatic score extraction from video. Encrypt clips and store bytes in a separate temporary MySQL table because the runtime object-store API cannot delete objects. Delete clips after the five-minute evidence window if the result is settled without review; hold them while a match/dispute is under review, then expire them five minutes after resolution. Restrict clip access to the uploader and authorized administrators; disclose that deletion removes the active database record but cannot guarantee erasure from backups. Never silently capture or record microphone audio.

## Delivery boundaries

Build and test against the project's existing resource configuration. Development, published production and migrations share the managed database: apply only checked-in additive schema changes and avoid destructive data tests. Configure SMTP using protected project secrets only for password-reset email; do not keep an email-based admin allowlist. Declare the partner signing key as a protected server secret; the partner purchase URL and KES enable flags are server-side configuration, not browser-supplied authority. Do not store or request MegaPay credentials in Pace Arena; the separate partner website owns checkout/STK. Runtime timeout polling is process-local but every database transition is revalidated under row locks; do not claim realtime push. Provide partner integration, operational limitations and backup guidance in the README. Do not claim gaming-publisher affiliation or independent screenshot/video authentication. The owner states that they hold a licence and have another licensed site, but this project has not verified that the licence covers Pace Arena or the integration; keep KES credits and wagering disabled by default until the partner contract and owner-approved launch configuration are supplied. Manual withdrawals are recorded only; the application does not send money. Do not represent the app as licensed or compliant without verification.
